# 03: Submit and edit a CS:GO submission

**What to build:** A mapper can create and edit a CS:GO submission end-to-end. Course names are prefilled and non-editable — the first course is `Main`, each added course becomes `Bonus 1`, `Bonus 2`, … following order. There is no port question, authorization upload, or porting rules step anywhere in the CS:GO flow, and the rules dialog shows the CS:GO rule set (the CS2 copy minus porting). The API enforces both rules server-side, while the CS2 form, schema, and rules stay exactly as they are.

**Blocked by:** 01, 02.

**Status:** ready-for-agent

- [x] On the CS:GO create form the first course is prefilled `Main` and its name is not editable; each "Add Course" appends a course prefilled `Bonus 1`, `Bonus 2`, … derived from position, and removing courses keeps the remaining names on-convention.
- [x] The CS:GO form shows no port section (no isPort question, no authorization image, no port notes).
- [x] The rules dialog on a CS:GO submission shows the CS:GO rule set — a copy of the CS2 steps minus the porting step — and the CS2 dialog is unchanged.
- [x] The shared wire schema rejects any port evidence on a CS:GO submission (must not be a port, no authorization image, no port notes).
- [x] The shared wire schema enforces the CS:GO course-name convention: exactly `Main` then `Bonus 1..N` in ascending order, `Main` mandatory and first, at least one course.
- [x] Editing a CS:GO submission keeps names derived and non-editable and the game fixed; editing a CS2 submission behaves exactly as today.

## Comments

Implemented 2026-09-11:

- **Course names by construction.** New `shared/utils/course-names.ts` is the single home of the convention: `csgoCourseNameForOrder` (1-based order → `Main`/`Bonus N`), `csgoCourseNamesMatchConvention` (exact ascending sequence; vacuous for empty — at-least-one stays the schema's `courses.min(1)`), and `courseNameForGame(game, orderIndex, fallback)` (derived for csgo, pass-through for cs2 — the one place the derivation rule is written). The form derives names in every path: `useSubmissionForm(game, initial)` prefills the blank create form with `Main`; `CourseEditorList` (now `game`-prop) derives on add and re-derives on remove so names stay on-convention after any mutation; `CourseEditorCard` renders the name field disabled for CS:GO; the edit page re-derives stored names from order in `toFormValue`. The payload sends state names as-is — they are always derived.
- **No port flow for CS:GO.** The form's isPort checkbox is gated on `!isCsgo`, the payload forces `isPort: false` / null port columns for CS:GO, and the CS:GO rules copy has no porting group (no port question in the dialog, no porting step).
- **Per-game rules.** `submissionRules.ts` keeps the CS2 `submissionRulesSteps` untouched and adds `csgoSubmissionRulesSteps` — written out as an independent literal copy of the CS2 rules minus the porting group (placeholder; the two games never share one rule set), plus `rulesStepsForGame(game)`. The rules dialog and both approver-checklist components (editable + readonly) now take a `game` prop and mirror `rulesStepsForGame`, so the porting step never renders on a CS:GO submission's checklist.
- **Wire schema per game.** `shared/schemas/submission.ts` extracts the shared base shape; `SubmissionInputSchema` (CS2) is behaviorally unchanged; new `CsgoSubmissionInputSchema` rejects isPort, any proof-of-permission image, and port notes, and enforces the course-name convention. `submissionInputSchemaFor(game)` dispatches, consumed by both the create and edit endpoints (the two write paths share one definition per game).
- **Cross-game mutation guard.** Code review (spec axis) caught that the edit endpoint validated against the *route's* schema without checking the row's own game — a direct `PUT /api/cs2/submissions/{csgoRow}` could write CS2-shaped content onto a CS:GO row. The guarded-write spine (`runGuardedWrite`) now takes the route `game` and refuses a row whose game differs with the same opaque 404 as a missing row; applied to both `updateSubmission` and `deleteSubmission` (and their bound entry points), so the row's game is fixed at creation and never mutatable through another context.
- **Mine list per game** was already delivered by ticket 01 (game-scoped reads via `ReviewQueueFilters.game`), covered at the endpoint seam (`index.get.spec.ts` scopes every delegated read to the requested game) and the review-queue seam; verified no regression.
- **Tests.** Seam A: `submission-input-schema.spec.ts` gains a `CsgoSubmissionInputSchema` block (port evidence each form + all at once, convention accept/reject incl. gap, non-`Main` first, stray `Main`, empty courses) plus the `submissionInputSchemaFor` dispatch; the CS2 cases stay green unchanged. Seam C: new `csgo-course-names.spec.ts` (derivation, convention predicate, `courseNameForGame`) and `approver-checklist-state.spec.ts` gains `rulesStepsForGame` coverage (CS:GO = CS2 minus porting, structurally independent objects, textual equality pinned, porting never rendered). Service seams: `update-`/`delete-submission.spec.ts` cover the cross-game 404 on both owner and lead paths (writes nothing, only the body's own fresh upload compensated).
- **Verification:** typecheck clean, lint clean (3 pre-existing `v-html` warnings only), full suite 370 tests passing (was 340 at ticket start). Reviewed via the two-axis code-review skill: both axes "OK with notes"; the spec P1 (cross-game edit) fixed as above, and the standards notes fixed — literal CS:GO rules copy (was a shallow filter), one derivation helper replacing three restatements, CONTEXT banned-term wording in new prose/messages ("Steps", "Authorization screenshot"), and dead `blankMapper`/`blankCourse` returns dropped from `useSubmissionForm`.
