# 02: Route Vote writes through the Review-write module

**What to build:** Approvers keep voting exactly as today — casting a Vote, re-saving it, proposing Course filters, attaching Rejection attachments to a `no` vote — but the write now runs through one Review-write module with the transaction guard inside: a Vote can never land after the submission has left `pending`, a same-approver double-submit is idempotent instead of a 500, a whitespace-only Rejection reason is rejected, and replaced attachment objects are deleted from storage only after the save commits.

**Blocked by:** 01

**Status:** resolved

- [x] A Review-write service module owns a transaction spine: re-read the submission inside the transaction, fail with a conflict when it is no longer `pending`, run the vote write, then compensate storage after commit.
- [x] The vote write is a single upsert on the unique (submission, approver) constraint — a same-approver double-submit is idempotent, never a unique-violation 500.
- [x] Saving a vote replaces its proposed Course filters wholesale and diffs its Rejection attachments, deleting replaced attachment objects from storage only after the commit.
- [x] The shared vote body schema enforces the rejection rules: a `no` vote requires a trimmed non-empty Rejection reason, and Rejection attachments are only valid on a `no` vote alongside a written reason; the rule-failure-to-error mapping exists once.
- [x] The vote endpoint is a thin adapter over the module; the previous vote service file is deleted.
- [x] Tests against an in-memory fake (writes apply to a scratch copy; success commits, failure discards): vote create and re-save via the upsert, Course-filter replacement, attachment replacement listing only removed URLs for storage deletion, whitespace-only reason rejected, attachments-on-approval rejected, and a vote whose submission left `pending` between the outer read and the in-transaction re-read fails without writing rows or deleting storage.

## Answer

Implemented in commit `a2b3e0d`. The new `server/services/review-write/` module owns the guarded write: `save-vote.ts` exports `createReviewWriteService(deps)` around a private `runGuardedWrite` spine (in-tx submission re-read → 404 missing / 409 left-`pending` conflict → kind-specific write step → post-commit storage compensation); `types.ts` defines the narrow `ReviewWriteStore` seam and deps; `drizzle-store.ts` is the real adapter (vote upsert via `onConflictDoUpdate` on the unique (submission, approver) index, wholesale filter and attachment replacement, normalized attachment rows); `index.ts` wires the production deps (real `withTransaction`, real `deleteStorageObjects`, real bucket scope) and exports the bound `saveVote`, so `vote.put.ts` is a thin parse-and-delegate adapter and `server/services/votes/save-vote.ts` is deleted. The shared schemas now require a trimmed non-empty reason on `no` votes and `rejected` decisions (`hasWrittenReason` in `shared/schemas/review.ts`), closing the whitespace-only hole issue 01 deliberately left open, and the rule-failure→error mapping lives once in the spine via `REJECTION_ATTACHMENT_MESSAGES`. Tests: `tests/server/services/review-write/save-vote.spec.ts` (10 cases) drives the module through the in-memory fake in `fake-review-write-store.ts` (scratch-copy commit/discard runner, recorded storage deletions, per-test `getSubmission` override to model the concurrent status flip), covering create/re-save upsert idempotence, wholesale filter replacement, attachment replacement with only-removed URLs deleted post-commit, whitespace-only reason rejection, attachments-on-approval rejection, the left-`pending` race (409, no rows, no storage ops), already-decided conflict, missing-submission 404, and rollback-on-throw with no compensation. The non-pending status error also moved from 400 to 409 (conflict). `pnpm lint` (0 errors), `pnpm typecheck`, `pnpm test` (107 passed), `pnpm build`, and `pnpm db:generate` (no schema changes) all pass. The decision write joins the same spine in issue 03.
