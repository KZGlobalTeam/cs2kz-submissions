# 03: Route Decision writes through the Review-write module and close the double-finalize window

**What to build:** The lead approver keeps finalizing exactly as today — approving with Finalized filters, rejecting with a Decision note and Rejection attachments — but the write now runs on the same Review-write module spine as the Vote, with the status guard inside the transaction. Two concurrent finalize attempts yield exactly one success: the loser rolls back instead of wiping the winner's Finalized filters. A decided submission is terminal by construction — a second finalize fails with a clear error rather than an empty 200 — and the decision request no longer carries the redundant ranked flag (derived from the filter state at write time).

## Answer

Implemented in commit `bafe617`. The Decision write now funnels through the same Review-write spine as the Vote: `server/services/review-write/save-vote.ts` adds `finalizeSubmission` to the service factory, sharing `runGuardedWrite` (in-transaction submission re-read → 404 missing / 409 left-`pending` conflict → kind-specific write step → post-commit storage compensation). The write step deletes and re-inserts the Finalized filters on approval (`replaceFinalFilters`, stamping the lead as `resolvedByUserId`) and clears them on rejection, writes the Decision attachment rows on rejection only (`insertDecisionAttachments`), then runs the guarded terminal status update (`completeSubmission` — a `.where(status = 'pending')` update); a zero-row result there raises a 409 conflict and the throw rolls the whole write back, so the losing concurrent finalize never commits its filter or attachment writes. The store seam (`types.ts`) gained `FinalFilterRecord` (`FinalFilterInput & { isRanked }`), `SubmissionDecisionWrite`, and the three store methods; `drizzle-store.ts` implements them (delete+reinsert of `submission_final_filters`, insert of `submission_decision_attachments`, guarded update returning `{ id, status }`); `index.ts` wires and exports the bound `finalizeSubmission`. `shared/schemas/review.ts` restructures the wire shape: a shared `FilterFieldsSchema` base is now extended by both `VoteFilterSchema` (keeps its own `isRanked` — a proposal has no `state`) and `FinalFilterSchema` (drops `isRanked`), and the write derives `isRanked = state === 'ranked'` before persisting, so the stored ranked column still reflects state on every row; `LeadDecisionPanel.vue` stops sending it. `decision.put.ts` is now a thin parse-and-delegate adapter and `server/services/submissions/finalize-submission.ts` is deleted. The same rejection rules hold on the decision wire via the shared schema (trimmed non-empty Decision note on rejection) and the shared attachment assessment in the spine (`REJECTION_ATTACHMENT_MESSAGES` — once, both paths). Tests: `tests/server/services/review-write/finalize-submission.spec.ts` (9 cases) drives the module through the extended fake (new `finalFilters` / `decisionAttachments` tables, `completeSubmission` override for the zero-row belt-and-braces case), covering approval with `isRanked` derived from mixed states, rejection attachments and cleared Finalized filters, attachments-on-approval rejection, the concurrent-finalize loser (status flips between the write starting and the in-tx re-read → 409, no rows, no storage ops), a second finalize after a Decision (409 conflict), the zero-row guarded update rollback, missing-submission 404, and the shared attachment-rule surface; the schema spec also covers the wire without `isRanked` and tolerating a redundant one (stripped). `pnpm lint` (0 errors), `pnpm typecheck`, `pnpm test` (117 passed), and `pnpm build` all pass. Known review notes (both axes P2, out of scope): in strict Postgres overlap the loser's final-filter insert can pre-empt the belt-and-braces 409 with a raw unique-violation 500 (the winner's data still survives and the loser rolls back — isolation is an out-of-scope framework fact), and the decision response narrowed to `{ id, status }` (the only consumer ignores it).
