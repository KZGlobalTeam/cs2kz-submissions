# Finalized filters carry no reasoning: the never-writable `notes` field is purged from the review side, and the release export keeps its placeholder for the external dashboard's import contract

The Finalized filter's `notes` field — free text that would have been the lead's settled reasoning beside the settled tiers and rank — was never writable. Since the lead decision form gained its Course-filter grid, the form's payload hardcoded the field to `null`: no input existed, no code path ever produced any other value, the Decision request schema accepted it, and the details payload shipped it back always-null. The decided view (the approver-votes section from the vote-history effort) derived a per-field "Final reference badge" from each Finalized filter, and the Reasoning row's Final badge therefore rendered a permanent `Final: —` placeholder — a settled reasoning that cannot exist, occupying the one row whose only honest content is the reasoning each approver actually proposed. The glossary even described the Filter note as attachable to a "proposed or finalized" Course filter, glossing a field that could never be filled on the finalized side. The settled rating is all a Finalized filter is.

Decision: the dead field is purged from the review side end to end, and the display model stops pretending a reasoning settlement exists. In the view (final-badges-reasoning-purge ticket 01), the Reasoning row no longer derives a Final entry at all — the section's display model renders proposals only, so no placeholder can ever surface. In the data model and pipeline (ticket 02), `notes` is removed from Finalized filters everywhere the review side touches them: the database column is dropped by migration `0009_rapid_red_shift.sql` — preceded by the documented pre-flight check that no row holds a non-null value, verified 0 of 32 before the column was dropped and all 32 rows survived — and the shared filter-fields schema is split so `notes` lives on the Vote proposal schema only (approvers keep writing reasoning when they vote) while the Decision request schema now rejects a body that carries it (`z.never()`), the decision write path persists final-filter records with no notes, the details payload type no longer carries the field, the release-contents store select, manifest type, and resolution stop reading it, and the lead decision form's payload stops sending its hardcoded `null`. The two decision sides now encode different truth and cannot drift: a Vote proposal may carry reasoning, a Finalized filter never does. This is the one deliberate split of the shared Course-filter wire shape ADR-0010 recorded for both write paths: the module's shared base — tiers, mode, state — survives intact, and `notes` moves to the Vote proposal side only.

The release export keeps its external contract (ADR-0008). The ordered manifest drops the field along with the review side, but the export shaping adapter re-synthesizes the `notes` key per finalized filter with the same `''` placeholder the documented null→`''` coercion always produced, so the JSON the operator pastes into the external CS2KZ dashboard's import dialog is byte-identical to today's. The shared snake_case export schema's nullable `notes` key is untouched — it is externally versioned by the dashboard's API shape, not by what the review side stores.

Considered: keeping the field for a future lead reasoning input — a home for reasoned justifications on the settled side when (or if) the lead ever gets such an input. Rejected: the field was dead from day one and the lead has never had, and no stakeholder asked for, a reasoning input at decision time — "neither built nor promised" — and keeping the field means keeping an always-null column, a schema key nothing can write, and a decided view that must keep inventing a settlement to render, which is precisely the placeholder this purge removes. The export contract gains nothing from the field's survival: the shaping adapter synthesizes the placeholder literally at the edge, so dropping the field upstream cannot change the payload, and reviving lead reasoning later is a clean additive change — re-add the column, the form input, and the schema key — that no dead field left behind today would ever be needed for. Compliance with the external contract is an export-concern, not a storage concern, and the two are now cleanly separated.

Consequences accepted: the review side can never render a settled reasoning — the Reasoning row on a decided submission shows only the reasoning each approver proposed, and anyone wanting a lead reason text must build the input, the column, and the schema surface deliberately, with this ADR recording why that revival should stay a conscious future decision rather than a default. No data was at risk: the migration's pre-flight contract checked every row and halted on any non-null value, none existed, and no backfill or historical-export rewrite was needed — the export is never persisted and is always rebuilt from live rows. Approver-proposed reasoning on Vote Course filters is untouched, and the external dashboard's import contract remains byte-identical (ADR-0008).
