# Submission-content writes go through one module: insert, replace, and delete on one guarded-write transaction, with the image lifecycle owned in full

The three submission write paths split the same responsibilities across files. The replace path copied the creator-gate sequence from delete (read the row → opaque 404 for a non-creator → count votes → `canMutateSubmission` → 409) and ~70 lines of content persistence from create (the 5-column port-authorization projection and the mapper/course/per-course-mapper insert loops), so the ADR-0002 mutability contract and the submission-content shape were each written twice and could drift. The image lifecycle was also split: stale-image cleanup ran post-commit in update and delete only, and a write that failed after uploads orphaned images — uploads persist immediately at `/api/uploads/*` under fresh UUID keys and there is no course or port-image delete endpoint, so nothing client-reachable could ever clean them up.

Decision: one submission-content module owns the three operations — insert, replace, delete — behind one guarded-write spine on one persistence seam. The spine re-reads the row inside the transaction, maps missing and non-creator to the same opaque 404, runs `canMutateSubmission` inside the transaction exactly as ADR-0002 requires (owner-or-unrestricted: pass the owner for the owner path, omit it for the lead approver's unrestricted delete), runs the kind-specific write step, then compensates storage after commit. Replace gains the same belt-and-braces the review-write module added: the content update targets the just-verified row and a zero-row match rolls the transaction back with the 409 instead of committing. The ~70 duplicated lines collapse into one internal content-write helper shared by insert and replace. The module owns the image lifecycle in full: post-commit stale-image cleanup on replace, post-commit full sweep on delete (course images, the port-authorization image, and vote/decision attachment objects — unchanged), and — new — orphan compensation on failed writes: when insert or replace fails mid-transaction after uploads, the module best-effort deletes the body's upload URLs that no persisted row references, so a failed write no longer piles up orphaned objects. That diff is safe because upload keys are fresh UUIDs per request and any URL carried over from a pre-filled edit is still referenced in the DB and therefore excluded; it is best-effort like post-commit cleanup and never fails the caller. The workshop-URL rule moves onto the shared wire schema: the client form's stricter rule (a `steamcommunity.com` workshop or sharedfiles filedetails URL with a numeric `id`) becomes a refine on `SubmissionInputSchema`, so an invalid URL dies at 400 at endpoint parse before any write, and `assertWorkshopId` becomes an internal happy-path derivation whose (now unreachable) failure maps to a 400 rather than a raw-Error 500; `extractWorkshopId` stays tolerant for legacy rows. The three endpoints become thin parse-and-delegate adapters over the module, and the delete endpoint's inline `roles.includes('lead_approver')` becomes a named predicate mirroring `hasApproverRole`. The transaction is bound through the same narrow-store pattern as the review-write module — a factory taking injected deps, a Drizzle adapter, and an in-memory fake for tests — so gate placement, the belt-and-braces rollback, and both compensation directions are unit-tested through the interface.

Alternatives considered: two operations — create+replace share "write content", delete stands alone (rejected: delete differs honestly — no content write, a different image job, an owner-optional gate — but it shares the largest behavior, the 404/409 gate semantics, so forcing it off the spine would re-duplicate the very thing being consolidated; three operations on one spine keeps the shared part in one place while the differences stay visible on the interface). Status-quo orphans — skip compensation on failed writes as the review-write module deliberately does (rejected: review-write attachments are few and re-saveable, whereas a submission-content retry loop accumulates images in a public bucket with no delete endpoint; the compensation closes a real accumulation bug and touches only URLs the DB no longer references). Schema-loose plus a bare raw-Error→400 fix (rejected: leaves the URL rule in three places with the stricter client copy duplicated; the wire shape is the one place both write paths already meet). Real-database integration tests (rejected for the same reason as ADR-0010: the repository has no DB test infrastructure, and what this changes is logical flow — guard placement, rollback, compensation — which an in-memory fake models faithfully).

Consequences: the ADR-0002 contract is written once but not changed — owner, `pending`, zero votes, gate inside the write transaction, lead path unrestricted; the belt-and-braces only narrows the ADR's recorded tolerated race (a vote committed in the same instant as the save can still have both observe zero votes), it does not close it. Pre-change orphaned uploads remain un-back-filled per ADR-0002. The failure-compensation direction deliberately diverges from the review-write module's accepted skip-on-failure for attachments. The client form's workshop-URL and map-name validation remain client-side copies; unifying the whole client/server validation gap on the shared schema is a follow-on ticket, not part of this consolidation.
