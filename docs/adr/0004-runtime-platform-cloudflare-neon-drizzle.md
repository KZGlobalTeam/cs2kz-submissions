# The app runs on Cloudflare Pages with a Neon serverless Postgres and Drizzle, and every request path is shaped around Workers constraints

Cloudflare Pages via Nitro's `cloudflare-pages` preset is the deployment target, chosen over a VPS specifically because Pages' git integration and built-in CI eliminate server setup and maintenance — the one category of work this project owner did not want. Storage is a Neon serverless Postgres database accessed through Drizzle. Because Workers forbid reusing I/O objects (WebSocket connections) across requests, all regular queries go through Neon's stateless HTTP driver (`neon()`, a cached client that issues a fresh `fetch()` per query), and only interactive transactions build a short-lived WebSocket `Pool` that is created and closed inside a single call — never cached, never shared (`db/client.ts`). The `nodejs_compat` compatibility flag is enabled at the framework level (`nitro.cloudflare.nodeCompat: true` in `nuxt.config.ts`, not in the dashboard) so `node:crypto` — required by Neon's SCRAM auth — is externalized to the Workers runtime instead of being inlined as unenv's unsupported stub; app-level hashing uses Web Crypto rather than `createHash`. One Cloudflare constraint shaped an API directly: Pages drops DELETE request bodies, so the rejection-attachment delete endpoint passes its target URL in the query string (commit `2df89b3`).

Considered: a conventional VPS/Node server was the realistic alternative, and it loses entirely on the setup-maintenance axis this project values. On the compatibility-flag layer, `wrangler.toml` was added, then removed once it seemed unnecessary, and re-added later solely to reproduce an issue from production — it is a debugging convenience, not a config source of truth. Consequences accepted: swapping hosts means re-validating the stateless-driver/one-shot-pool transaction pattern, the crypto assumptions, and the DELETE-body workaround; any future delete endpoint inherits the query-string constraint.
