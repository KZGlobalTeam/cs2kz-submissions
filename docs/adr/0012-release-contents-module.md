# The Release export and the Image pack render one ordered manifest resolved by a single release-contents module

The Release JSON export and the Image pack ZIP each re-ran the same release → submissions → courses → filters aggregation with an identical approved-only guard, and silently disagreed on ordering. `build-export.ts` walked links → submissions → course-final-filters → course-mappers and sorted nothing — its output order was whatever `inArray`/insertion returned, and since the external CS2KZ dashboard identifies courses by name with `NewCourseSchema` carrying no order field, that array position is the only positional signal the import gets. `build-image-pack.ts` walked links → submissions → courses and sorted maps by `createdAt` ascending with a map-name tie-break and courses by raw `orderIndex`, throwing the identical message `'Release contains non-approved submission'` from a second copy of the same guard. Two more asymmetries lurked: an unknown release id made the pack 404 while the export silently returned `[]` — and still stamped `exportedAt` on a row that does not exist; and the pack's `orderIndex`-ordered courses described the same sequence the export emitted in unspecified order.

Decision: one release-contents module resolves a release's **ordered manifest** once, and both artifacts render from it as thin formatting adapters. The module follows the review-write (ADR-0010) and submission-content (ADR-0011) shape: a narrow read-mostly `ReleaseContentsStore` port (`types.ts`) — `getRelease`, `listLinkedSubmissionIds`, `listMaps`, `listCourses`, `listMapMappers`, `listCourseMappers`, `listFinalFilters`, `markExported` — bound to the Drizzle HTTP client in `drizzle-store.ts`, with a `createReleaseContentsService({ store })` factory (`resolve-release-contents.ts`) owning **assembly, ordering, and the guards**, and `index.ts` wiring the production store and exposing the bound `resolveReleaseContents` and `markReleaseExported`. The manifest is the superset both artifacts need — release name; maps with `mapName`, `workshopId`, `createdAt`, map mappers, and courses; each course with `courseId`, `orderIndex`, `name`, `imageUrl`, course mappers, and its classic/vanilla finalized filters (mode-absent courses carry `null` — the manifest does not judge presence). The ordering rule is defined once, in the spine: maps by `createdAt` ascending with `mapName` ascending as tie-break, courses by `orderIndex` ascending, mappers in table insertion order. The approved-only guard lives in the resolution with its single 400 message, so both artifacts fail identically at resolution before any artifact-specific output exists; an unknown release is a single 404, which changes the export's stale-id behavior from an empty payload (and a phantom `exportedAt` write) to not-found. An empty release still resolves to `maps: []`, and each artifact keeps its own empty semantics: the export renders `[]`, the pack-builder keeps its `no maps to pack` 400. The missing-finalized-filters refusal remains an export concern (`toReleaseExportPayload` throws the course-naming 400; the pack renders no filters and keeps working). `exportedAt` stays exactly where ADR-0008 documents it — a read with a state-changing side effect, owned by the export handler — now invoked as the module's explicit `markReleaseExported`, so the image pack download never marks a release exported.

The two pure seams the report identified are preserved untouched: `toReleaseExport` (`server/utils/export-release.ts`) remains the DB-rows → `NewMapSchema`-validated payload formatter, and `buildImagePack`/`toImagePackStream` (`server/utils/image-pack.ts`) remains the pure streaming ZIP generator with its injected `ImagePackFetcher`. Each gains one adjacent pure shape-mapper — `toReleaseExportPayload` and `toImagePackManifest` — so the adapters (`build-export.ts`, `build-image-pack.ts`) are thin bound wrappers: resolve once, shape. Specs follow the repository's pure-test convention: the spine is driven against an in-memory fake store (`tests/server/services/release-contents/`), and the shape-mappers are spec'd next to the formatter seams they feed (`tests/server/utils/export-release.spec.ts`, `image-pack.spec.ts`). Neither the raw `db()` aggregation nor the handlers are unit-tested, matching prior art.

Alternatives considered: keep the two resolutions and only share a sorting helper (rejected — the duplicated 4-step aggregation and duplicated guard were the finding; sharing an order function leaves the divergence intact); have the resolution return only the shared core and let the export re-query mappers/filters (rejected — that splits the aggregation back in half and preserves a second read path); move `markExported` into the shared resolution so both handlers stamp it (rejected — the image pack has no side effects by design, so the side effect must stay exclusive to the export path; the module owns it for locality while only the export handler calls it); normalize the empty release to a 400 in the resolution (rejected — exporting an empty release is not an error the UI should defensively handle, and the pack-builder already owns its empty-archive refusal).

Consequences: the aggregation and the guard exist once — the export and the pack cannot silently diverge on ordering again, and a fourth artifact (N artifacts, one resolution) now adds only a shape-mapper. The export's stale-release-id behavior tightened from empty payload + phantom `exportedAt` to 404; course arrays in the export JSON are now deterministically `orderIndex`-ordered, which is strictly more information than the insertion order the dashboard previously received. The resolution loads finalized filters even when only packing (a bounded extra read that keeps the aggregation single-pass); the filters' presence judgment stays export-side. `NewCourseSchema` remains externally versioned: if the CS2KZ API's import dialog ever needs course order carried explicitly, that is a change to the shared schema, not to this module.
