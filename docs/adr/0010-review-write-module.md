# Review writes go through one module: a shared Course-filter wire shape, one rejection-rule surface, and an in-transaction status guard

Vote and Decision writes carried the same Course-filter payload but re-typed it at every layer: the ten-tier difficulty list existed in shared code (`courseFilterTierValues`), in the DB enum, and inline in both write endpoints, and the zod schemas the shared module already exported were used for their inferred types only — never validated against at runtime. Rejection rules split across endpoint validation and the attachment-list module with different semantics: the endpoints only checked truthiness of the reason, so a whitespace-only reason sailed through and was stored, while the attachment-list module required a trimmed non-empty reason only when attachments were present. And both write services guarded the `pending` status *outside* the transaction, unlike the owner edit/delete path (ADR-0002) which had already moved its guard inside.

Decision: one review-write module owns the whole write surface — the Course-filter wire shape, the rejection rules, and the guarded transaction — and both write endpoints become thin adapters over it. The Course-filter wire shape is defined once in shared code by composing the existing tier/mode/state schemas; both endpoints parse against it; the input types the services consume are inferred from it; and the DB enums derive from the same shared value arrays, so adding a tier touches exactly one file. The rejection reason rule moves into the shared body schema as the documented-domain rule (a rejection carries a required reason, trimmed), the attachment-list rules stay in the attachment-rules module, and the mapping from rule failure to an error response exists once, in the spine. The status guard moves inside the transaction — re-read the submission, fail the write on any non-`pending` status, run the kind-specific write, then compensate storage after commit — matching the owner path's established pattern. This closes the race window ADR-0007 recorded as accepted: a losing concurrent finalize now sees the winner's status change at the re-read and rolls back, instead of deleting and re-inserting final filters and writing decision attachments for a zero-row status update that returned an empty 200. Vote saves become a single upsert on the unique (submission, approver) constraint, which makes a same-approver double-submit idempotent instead of a unique-violation 500. `isRanked` is dropped from the Decision wire and derived from `state` at write time (the column stays for reads); Vote proposals keep their own `isRanked`, since a proposal carries no `state`.

Alternatives considered: a single entry point taking a discriminated vote-or-decision payload (rejected — vote upserts and stays one of many, decision is one-shot and terminal; the union would be one function hiding genuinely different write semantics behind a switch, and the shared spine already gives the single implementation the report asked for without flattening the two behaviors); keeping both `isRanked` and `state` on the wire and enforcing the invariant with a refine (rejected — the client already derives `isRanked`, so a check only catches a client bug; deriving at the write removes the redundancy by construction); real-database integration tests via pg-mem (rejected — the repository has no database test infrastructure, and what the rework changes is logical flow — guard placement, rollback-on-throw, compensation skipping — which an in-memory fake models faithfully; Postgres-level uniqueness and isolation remain framework facts).

Consequences: one place to define the Course-filter shape and the rejection rules; the double-finalize window closed; and a testable seam — the transaction spine depends on a narrow store interface, so the guard placement, rollback, and compensation behavior are unit-tested with an in-memory fake in the repository's existing pure-test style rather than against a live database. Accepted: the Postgres transaction contract itself is not re-tested, and the client's stricter vote-form rule (reasoning required per enabled filter) remains a client-only rule.
