# Approver rule checklists and notes live in a private per-approver table, not on the vote

Approvers get a section next to the vote form: a check-off of the same grouped rules the mapper acknowledges before submitting (single source of truth: the shared `submissionRules` module), plus a free-text note. The ticks and note are a private working aid — visible only to the approver who wrote them, never to other approvers, the lead approver, or the submitting mapper — and they persist across sessions without requiring a cast vote, surfacing read-only on the submission page once the map leaves review.

We store them in a dedicated `submission_approver_checklists` table keyed by (submission, approver), written by their own `GET/PUT /api/submissions/[id]/approver-checklist` endpoints with a precise `approver`-role check: the caller must hold the `approver` role — a user who also holds `lead_approver` is still an approver and reads/writes only their own checklist. The shared `requireApprover` deliberately admits lead-*only* users too, which this feature must not, so the endpoints use their own predicate (`hasApproverRole`). Saving is debounced auto-save, flushed when the vote is saved or the view unmounts. Considered: columns on `submission_votes` — rejected because votes are shared payload: every approver sees every vote (filter details, summaries), and the votes array is folded into the submission-detail response, so piggybacking would require stripping the private fields from every consumer and risk a forgotten leak; it would also tie scratchpad persistence to the vote lifecycle, losing ticks before the first Save. Considered: client-only — rejected because review spans sessions and devices, and the note/ticks must survive. Consequences accepted: rule ticks are per-index booleans within each rule group, so if the shared rule *text* changes (e.g. the map-name length cap), a stored tick can sit against the updated text of the same index — harmless for a private scratchpad, and the text itself always renders from the single shared rules module; and the section is deliberately absent for lead-*only* users, who judge votes but never see approvers' private verification state (an approver who also holds the lead role sees only their own checklist, like any other approver).
