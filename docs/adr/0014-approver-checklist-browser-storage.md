# The Approver checklist and note live in the viewer's browser — per-account local storage behind an injectable adapter, written through on every change, with no server surface

The Approver checklist and Approver note are a purely personal working aid: only the approver who wrote them may ever see them, they appear in no vote summary and never influence other approvers or the lead approver, and they are explicitly not a review artifact. The first version of this feature kept them in a dedicated server-side per-approver table, written by its own endpoints with a checklist-specific role predicate (ADR-0003, which this decision supersedes). That worked, but it paid for a whole server surface — a table, two endpoints, a request schema, a role predicate, and their tests — purely to hold data that should never leave its author's browser. The re-scoped decision replaces that surface with browser storage: the same section next to the vote form, the same immediate saving, the same read-only surfacing once the submission has left review — nothing checklist-related is ever sent to the server.

Decision: the Approver checklist and Approver note live in the viewer's own browser, in local storage behind a thin injectable storage adapter that owns all access — key composition, serialization, writes, clearing, and cross-tab change handling — and whose real backend can be swapped for a test double. The storage key is derived from the viewer's session user id and the submission id, so two review accounts sharing a browser never read each other's state; the id comes from the session the server already authenticates. Every tick or note change is written through synchronously as it happens — there is no debounce, no pending-writes flush, and no saved indicator — so a vote save or a view unmount can never lose unpersisted work. Ticks are stored per rule group and index and the rule text always renders from the single shared rules module, so a rule-text edit propagates to both the pre-submission dialog and the section without any migration or data reshaping. When every tick is cleared and the note is emptied, the stored key is deleted entirely: "reset to nothing" and "never saved" are deliberately indistinguishable, which is what hides empty boxes on finished submissions. Cross-tab changes are adopted per field, newer write wins, and another tab removing the key resets the state to empty; the tab that made the change applies its own state directly rather than through the event. Storage read or write failures — storage disabled, quota exceeded — are caught and degrade to a fully usable in-memory session rather than blocking review. The only server involvement left is deciding whether the section renders at all — whether the viewer holds the approver role — from the session the server already provides.

Considered: keeping the per-approver table (ADR-0003) — rejected because the data is a private scratchpad that must never leave its author's browser, so the table, endpoints, predicate, schema, and tests exist solely to hold it; server-side storage would also keep the checklist permanently available across browsers and devices, which is beyond what any stakeholder asked for, and would preserve a maintenance surface the re-scope deletes outright. Considered: dual-write — persisting to both the browser and the server table together — rejected because it answers a loss mode nobody named as a requirement, keeps the entire server surface alive, forces a decision about which copy wins when they disagree, and quietly re-raises the question of who may ever read the stored copy. The decision is browser-only, with the loss modes documented and accepted below.

Consequences accepted: the checklist and note persist only in the browser where they were written — a cache clear, a private-browsing session, or a different browser, profile, or device loses them, and the read-only record after review is equally per-browser, so approvers who review across devices should expect their scratchpad to follow them only within the browser where they wrote it. Cross-tab sync keeps multiple tabs of the same browser consistent — per-field adoption, newer write wins, another tab removing the key resets the state to empty — but it is deliberately not cross-device: it extends the same per-browser state to other tabs, never to another browser. Shared-browser keying keeps one account's state invisible to another; the residual exposure — a party who already has access to the browser's storage and knows another account's user id could read that account's key — is accepted as outside the threat model. Ticks are per-index booleans within each rule group, so after a rule-text edit a stored tick can sit against the updated text at the same index — harmless for a private scratchpad, and the text itself always renders from the shared rules module. Orphaned keys left after a submission is deleted are accepted: they are tiny and keyed by a submission id that never recurs. And an approver on a browser where storage is unavailable still gets the section working for the session, minus persistence.
