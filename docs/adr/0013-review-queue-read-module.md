# The review-queue read is one module: a shared predicate builder, a statement-granular store seam, and row types derived from the assembly

The submissions list/count reads rebuilt the same where-clause four times in `server/queries/list-submissions.ts`: `listOwnSubmissions` and `countOwnSubmissions` repeated the identical status-owner ternary, and `countAllSubmissions` and `listAllSubmissionsForReview` each built the same conditions array — while the unvoted guard was asymmetric by construction (`unvotedOnly && userId` on the count, `if (unvotedOnly)` on the list), so the two could disagree about which rows matched. The review-queue list also ran four parallel aggregates into three hand-rolled Maps and serialized timestamps to ISO inside the query layer, and the `ReviewSubmissionRow` it returned was hand-defined in shared code and kept in sync manually. Its only callers were one endpoint, which silently degraded invalid `?status=`/`?scope=` values to "no filter" (showing *more* rows than asked), and two client pages via `usePaginatedTable`. A sibling votes query, `server/services/votes/list-votes.ts`, was never imported at all.

Decision: one review-queue read module owns all four submissions reads — the mine pair and the review-queue pair. It lives at `server/services/review-queue/`, mirroring ADR-0010's layout: a `types.ts` holding the narrow store seam and the filter value, a `createReviewQueueRead(store)` factory, and a `drizzle-store.ts` adapter; tests drive the same aggregation through an in-memory fake in the repository's established local-substitutable style. The module's surface is two methods — `getMinePage(filters, bounds)` and `getQueuePage(filters, bounds)` — each running its list and count inside against the *same* filters value, so a caller cannot call list with different predicates than count: "count derives from the same predicates" moves from convention to structure. The predicates are one discriminated value, `{ status?: SubmissionStatus } & ({ ownerId: string } | { unvoted: { userId: string } })`, which makes `unvoted` impossible to express without its user — the old count/list guard asymmetry becomes a type error. A pure `resolveFilters` turns that value into `{ status?, ownerId?, unvotedUserId? }`, and *both* the Drizzle adapter (which maps it to `and(...)` conditions, including the correlated `NOT EXISTS` for unvoted) and the fake store (which filters its in-memory rows) consume the same resolved object, so the rule is pinned in one place and enforced identically by the real read and the test read. The store seam is statement-granular — `listSubmissionsPage`, `countSubmissions`, `listMappers`, `countVotesByDecision`, `listMyVotes`, `countCourses` — so the aggregation (Maps, yes/no defaults, myVote precedence, timestamp serialization, per-read ordering) stays in the module: the module stays deep, the adapter stays thin SQL, and the fake stays a dumb in-memory table; the mine row's `voteCount` reuses `countVotesByDecision` (yes+no), so one aggregate serves both assemblies. `ReviewSubmissionRow` and `OwnSubmissionRow` are derived from their assemblies in the module, the hand-synced interface leaves `shared/types/submission.ts`, and the two pages (`pages/review/index.vue`, `pages/releases/new.vue`) move to type-only imports from the module path — safe across the Nuxt client/server boundary because they are erased at build. The endpoint becomes a thin adapter: `status`/`scope` are zod-validated with a 400 on invalid input and `undefined` when absent, `unvoted` stays the coarse `=== 'true'` flag, and `parsePagination` is untouched (its silent fallback is a contract shared with the approvers and releases endpoints). `server/queries/list-submissions.ts` is deleted outright, and `server/services/votes/list-votes.ts` with it; `server/queries/submission-details.ts` stays untouched — its votes query is detail-shaped (per-vote rows, approver names, attachments, filters) rather than dead, and sharing a votes helper with the queue read would be a shallow pass-through. Ordering is fixed per read inside the module, exactly as today: the queue orders by `approvedAt` desc when the status filter is `approved` and by `createdAt` desc otherwise; mine orders by `createdAt` desc. The derivation of Unreviewed vs In review from votes is not re-opened (ADR-0007), and no new domain concept is introduced — CONTEXT.md already names the review queue.

Alternatives considered: a mission-literal review-queue-only read leaving the mine pair in place (rejected — the `owner` predicate belongs to the mine pair, which carries the identical duplication, and one module fixes all four call sites and deletes the query file outright); a coarse `loadForReview(filters, bounds)` store bundle returning pre-joined rows (rejected — it pushes the aggregation into the adapter and forces the fake to reimplement it, leaving a shallow module and less test coverage); a pure-function assembly split tested with hand-built flat rows and no store seam (rejected — the review report asks for an injected data seam, and without one the SQL layer and guard placement stay untested); keeping the four list/count exports and the endpoint's `Promise.all` (rejected — the combined methods make the count/list invariant structural, not a caller obligation); keeping the hand-synced row type behind a compile-time `Equal` tripwire (rejected — two sources of truth instead of one); and making `parsePagination` throw on invalid input within this work (rejected — its contract spans three endpoints, and its silent fallback is plausibly deliberate defensive behavior).

Consequences: one place defines the predicates, the aggregation, and the row shapes; list and count cannot drift by construction, and the fake enforces the same filter rule at runtime; the aggregation is unit-tested for the first time, so the recent hot spot (course counts, unvoted filter) gets regression coverage in CI without a live database; the submissions endpoint stops silently over-returning on invalid filters; and the first read module joins `server/services/` while `submission-details.ts` and `list-releases.ts` stay in `server/queries/` until they grow specs. Accepted: `parsePagination` remains untested with its silent fallback (a candidate for its own spec, out of scope here), and Postgres-level query plans remain framework facts.
