# Votes are advisory; the lead approver alone finalizes, and a decided submission is terminal

The review workflow: approvers cast Votes, and the first vote is what moves a submission from Unreviewed to In review, closing the submitter's edit/delete window (ADR-0002). There is no quorum, aggregation, or resolution rule anywhere in the app: the Decision is purely the lead approver's discretion, and other approvers' votes and proposed course filters are reference information only — surfaced as badges in the decision panel, never tallied into an outcome. Finalization is one-shot: the status update carries a still-`pending` predicate so a concurrent double-finalize matches zero rows, final filters are deleted and rewritten exactly once, and decision attachments are written once and never edited. A decided submission is terminal: approved or rejected, it can never re-enter review or be re-submitted — fixing a rejected submission means creating a new one.

The submission's terminal status is persisted as an enum (`pending`/`approved`/`rejected`), but whether a pending submission is Unreviewed or In review is never stored — it is derived on every read, and inside the ADR-0002 mutability gate, from whether any vote exists. Storing the sub-state would add a second source of truth that every vote write would have to keep in sync for no benefit, since the vote count is computed in the same transaction anyway. Consequences accepted: a race window exists where an in-flight vote and a concurrent finalize can interleave (tolerated at this scale); the schema technically permits a status flip back to `pending`, but no code path does it.
