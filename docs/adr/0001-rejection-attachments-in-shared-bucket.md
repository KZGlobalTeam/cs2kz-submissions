# Rejection attachments live in the shared public storage bucket, gated at the API

Rejection attachments (approver-internal screenshots, plus the lead approver's rejection images that are revealed to the mapper once a decision is finalized) are stored in the same public Supabase bucket as course and authorization images, under a `rejection-attachments/` key prefix, with plain public URLs. All protection lives at the API layer: vote rows — and therefore their attachments — are stripped server-side for non-reviewers; both vote and decision saves validate that every attachment URL points at the bucket's `rejection-attachments/` prefix, so reviewers cannot inject arbitrary URLs into a rejection; and removing an attachment deletes its storage object. A private bucket with signed URLs was considered and rejected: it would require new environment configuration, new Supabase setup, and per-render URL signing across the read path, for images that are internal moderation material in a small trusted team — the shared bucket is zero-config and consistent with every other image in the system. Consequences that are accepted, not accidental: anyone holding a URL can open an image (end-user protection is deliberately at the API layer), and abandoned or orphaned staged uploads may leave objects in storage.
